# 密钥保护与「解锁口令」机制说明书

> **一句话先说清**：这个「口令」是你给**浏览器里一个临时保险箱**设的开箱密码，和网站账号、和你的 API Key 都不是一回事。**不填它，网站照常能用**；填它，只是为了「刷新页面后不用重新粘贴 API Key」。

如果你只是想赶紧用起来，记住三句话就够了：

1. **API Key**（`sk-...` 那种）是服务商给你的，用来让 AI 干活。
2. **解锁口令**是你自己随便设的（至少 8 位），只用来把 Key 临时锁在本标签页里。
3. **口令忘了没法找回，但一点都不严重**——点「彻底清除」，重新粘一次 API Key、重新设个新口令就行，你的 Key 本身没有丢。

下面把整个机制讲清楚。

---

## 一、先把三个东西分开（最容易搞混的地方）

本站**没有账号、没有注册、没有登录**，所以很多人会把这几样混成一个。请对照这张表：

| 名称 | 它到底是什么 | 谁给你的 | 存在哪里 | 忘了 / 丢了会怎样 |
|---|---|---|---|---|
| **API Key**（密钥） | 服务商发给你的一串 `sk-...`，浏览器拿它放在请求头里向 AI 服务商发请求 | AI 服务商（DeepSeek、OpenAI、智谱、Kimi…）在它的控制台给你 | 你填进网站后，**只在本站运行的内存里** | 去服务商控制台重新生成一把即可，本站无需任何「找回」操作 |
| **解锁口令**（本说明的主角） | 你自己临时编的一串字符，**只是本地加密用的密码** | **你自己**，随便设，≥8 位 | **哪里都不存**——只在你脑子里，用完即弃 | **无法找回，也没有「找回密码」功能**；但不影响重新填 Key，详见 FAQ 第 1 条 |
| **网站密码** | —— | —— | —— | **不存在**。本站没有账号体系，任何地方都不会让你「注册 / 登录」 |

> ⚠️ 特别提醒：**不要把你的 API Key 当成口令填进去，也不要把常用网站密码当口令用**。口令只是给本地保险箱上锁用的，随便编一串你自己记得住、别人猜不到的就行。

---

## 二、为什么需要这个机制？它解决什么问题

本站是**纯静态网页**：没有后端服务器、没有数据库、没有任何中转。你填的 API Key 必须由浏览器直接放进请求头发给你自己配置的服务商。

这就带来一个绕不开的事实：**发请求的那一刻，浏览器手里必须拿着明文的 Key**。我们要解决的问题不是「让浏览器永远拿不到 Key」（纯前端做不到），而是：

> **在不用 AI 的时候，尽量别把这串明文 Key 留在电脑硬盘上。**

于是有两种用法，由你自己选：

- **默认（什么都不设）**：Key 只放在内存里。刷新页面、关掉标签页，Key 立刻消失。**最安全，代价是每次刷新都要重新粘贴一遍 Key。**
- **可选（设了口令）**：用口令把 Key 加密后，临时寄存在**当前这个标签页**里。刷新页面后输一次口令就能恢复，不用重贴 Key。**方便一些，代价是电脑上有了一份加密的密文。**

「密钥保护」这一小块面板，就是让你在这两种用法之间切换、并随时查看当前状态的。

## 三、设与不设，到底差在哪

| 对比项 | 不设口令（默认 / 推荐在公共电脑） | 设置口令并点「会话内记住」 |
|---|---|---|
| 刷新页面后 | 需要重新粘贴 API Key | 输入口令点「解锁」即可恢复，不用重贴 Key |
| 关闭标签页后 | 全部消失 | 全部消失（密文本来就只活在这个标签页里） |
| 电脑上留下的东西 | **什么都没有** | sessionStorage 里一份 **AES-256-GCM 密文**（没有口令解不开） |
| 明文 Key 会不会写进硬盘 | 不会 | 不会（写进去的永远是密文） |
| 导出备份里有没有 Key | 没有 | 没有 |
| 适合场景 | 公用电脑、临时用一次、最在意安全 | 自己的电脑、一个下午要反复刷新页面 |
| 安全等级 | 更高 | 略低，但仍是加密暂存、且自动过期 |

**结论：不确定就用默认（不设口令）。** 它只是让你多贴一次 Key，换来的是「电脑上不留任何痕迹」。

## 四、面板上三种状态怎么看懂

| 显示 | 颜色 | 含义 | 你该做什么 |
|---|---|---|---|
| `● 已解锁（N 把密钥在内存中）` | 绿色 | 明文 Key 现在正在内存里，可以正常向 AI 提问 | 正常用；用完可点「立即锁定」 |
| `● 已锁定 · 存在加密暂存（至 HH:MM），输入口令解锁` | 黄色 | 内存里没有明文了，但有一份密文等你解锁 | 在输入框填口令 → 点「解锁」 |
| `● 已锁定 · 无暂存，请重新输入 API Key` | 红色 | 内存和暂存都没有密钥 | 回到上面的 API Key 输入框重新粘贴 |

输入框的提示文字也会跟着变：需要解锁时显示「输入解锁口令」，平时显示「设置解锁口令（至少 8 位）」。

## 五、四个按钮分别是干什么的

| 按钮 | 作用 | 什么时候出现 |
|---|---|---|
| **会话内记住** | 用你填的口令，把当前内存里的 Key 加密暂存到本标签页 | 已解锁时 |
| **解锁** | 用口令把密文解回内存，恢复提问能力 | 已锁定且有暂存时 |
| **立即锁定** | 立刻清掉内存里的明文 Key，**保留**那份密文（之后可用口令解锁） | 已解锁时 |
| **彻底清除** | 内存明文 + 加密暂存**一起销毁**，不可恢复 | 已解锁或有暂存时 |

> 「立即锁定」是临时锁屏；「彻底清除」是全部抹掉。想换一把 API Key、或者用完公共电脑，请用**彻底清除**。

## 六、它会自动锁上吗？会，规则如下

不需要你记着手动锁，以下任一情况都会自动清空内存里的明文 Key：

| 触发条件 | 时间 |
|---|---|
| 没有任何 AI 请求（空闲） | **15 分钟** |
| 页面被切到后台 / 最小化 / 切到别的标签页 | **3 分钟** |
| 刷新页面、关闭标签页、页面被系统冻结 | 立即 |
| 加密暂存到期 | **8 小时** |
| 主动点「立即锁定」/「彻底清除」 | 立即 |

刷新或关闭页面时，内存明文被擦掉，但那份密文会**特意保留**（因为存在 sessionStorage 里，刷新不会清），这样你回来输口令就能解锁；而**关掉整个标签页，sessionStorage 就没了，密文也一起消失**。

另外：**只要你重新粘贴 / 修改了 API Key，旧的加密暂存会立刻作废**，避免解锁出过期的旧密钥，需要重新设一次。

## 七、技术细节（想深究再看，跳过不影响使用）

- **密钥派生**：`PBKDF2-SHA256`，**310,000 轮**，配 16 字节随机 salt。口令从不明文保存，只作为派生输入。
- **加密算法**：`AES-256-GCM`（带认证，密文被改动一个字节都会解密失败），配 12 字节随机 IV。
- **实现**：浏览器原生 Web Crypto；派生出的 `CryptoKey` 设为**不可导出**（`extractable: false`）。
- **存放位置**：密文只写入 `sessionStorage`（键 `byok.vault.v1.blob`），**从不写 `localStorage`、Cookie、IndexedDB**；标签页关闭即由浏览器清除。
- **口令与明文**：口令本身、明文 Key 都**永不落盘**，也不进入 URL、Referer、错误堆栈、导出备份、日志或任何可序列化对象。
- **配置里存的不是 Key**：保存的设置里只有一个句柄，形如 `@byok-vault:default`，它**完全不能用来发请求**；真正的 Key 只在模块私有的内存 Map 里。
- **对外展示**：只暴露 SHA-256 前 8 位指纹用于「这是哪把 Key」的辨认，不暴露明文。
- **单一出口**：界面组件拿不到明文，只有真正发请求的那一层才临时取用，用完即弃。

口令错误、密文被篡改、暂存已过期，这三种情况在程序里是同一个结果：**解锁失败**。这是刻意的，避免向攻击者泄露「到底是口令错了还是数据坏了」。

## 八、常见问题（FAQ）

**1. 口令忘了怎么办？能找回吗？**
不能，本站不存口令，也没有「找回密码 / 邮箱验证 / 密保问题」。但**这不是事故**：点「彻底清除」把旧暂存删掉，重新粘贴一次 API Key，再设一个新口令即可。你的 API Key 没有丢——它还在服务商控制台里，随时可以复制或重新生成。**唯一损失是那份「不用重贴 Key」的便利，重新设一次就恢复了。**

**2. 口令会不会被上传到服务器 / 服务商？**
不会。本站没有服务器；口令只在浏览器本地参与 `PBKDF2` 计算，从不进入任何网络请求，也不写进 localStorage。发往 AI 服务商的请求里只有 API Key，没有口令。

**3. 口令要设多复杂？要不要和别的账号密码一样？**
建议 **≥8 位、别用生日 / 12345678 这类、别和你的常用密码相同**。它只在本标签页短期有效（最长 8 小时），风险远低于账号密码，但仍值得认真设一个。系统只强制「至少 8 位」，不强制特殊字符。

**4. 为什么刷新页面后还要我输一次口令？**
因为刷新会清空内存里的明文 Key，只剩密文。输口令是为了把密文解密回内存——**这正是这个机制在起作用**，不是出错。若不设口令，刷新后要重贴整把 API Key，反而更麻烦。

**5. 为什么关掉标签页就全没了？**
`sessionStorage` 的生命周期就是「这个标签页」。这是刻意设计：不希望你的密钥长期留在电脑上。换新标签页、关掉重开，都需要重新来一遍。

**6. 我明明设了口令，怎么过了一晚上又要重填？**
暂存有效期 **8 小时**，过期自动作废。这是安全兜底，不能延长。

**7. 在公共 / 共用电脑上怎么用最安全？**
**不要设口令、不要点「会话内记住」**；用完点「彻底清除」，然后**关掉标签页**（不是只关窗口）。最稳妥的是用完顺手清理一下浏览器数据。

**8. 设了口令，是不是就绝对安全了？**
**不是，请不要这样理解。** 详见下一节。

**9. 我导出 / 导入备份，会把密钥带出去吗？**
不会。导出文件**永远不包含 API Key，也不包含口令**，只包含不含密钥的句柄标记；换设备后需要重新粘贴 Key。

**10. 不填口令，网站会不能用吗？**
完全不会。默认就是「不填」，所有功能照常，只是每次刷新页面要重新粘贴一次 API Key。

## 九、必须如实说清的安全边界

请把这一段读完，不要让「保险库」三个字给你错误的安全感。

> **纯前端 BYOK 存在一个绕不开的不可能三角**：只要浏览器需要把明文 Key 放进 `Authorization` 请求头，同源执行的脚本就有能力读到它。因此，**如果页面被注入了恶意脚本（XSS），攻击者仍可能在密钥解锁期间 hook `fetch` 或读取内存**。

本机制能做到的，是把「**长期躺在硬盘上、随时可读的明文**」变成「**短暂存在于内存里的明文**」，并配合站点严格的 CSP（内容安全策略）尽量堵死脚本注入这条路。它显著降低了「别人拿到你电脑 / 翻浏览器存储 / 你导出的备份被传播」这几类风险，但**不能宣称「绝对不会泄露」**。

要让浏览器**永不持有**明文 Key，唯一根治方案是「服务端代理 + HttpOnly 会话」——本站**刻意不采用**（那样就有了后端、要托管、要信任服务器，与本项目「纯静态、零收集」的定位冲突）。

因此请务必配合以下使用习惯：

- 使用**额度受限、可随时撤销的专用子密钥**，不要用主账号密钥，不要在这类站点填高权限 Key。
- 定期在服务商控制台轮换 Key；怀疑泄露立即撤销。
- 只从官方 / 你自己信任的站点地址打开，不要点来路不明的镜像站。
- 公共电脑用默认（不设口令），用完「彻底清除」并关闭标签页。

## 十、给开发者：接口速查

`src/lib/byokVault.ts`（浮生项目为 `byok-vault.js`）导出一个模块级单例 `vault`：

| 接口 | 用途 |
|---|---|
| `set(slot, apiKey)` | 把明文 Key 放进内存；会作废旧暂存 |
| `get(slot)` | **仅请求层调用**，取明文，用完即弃 |
| `has(slot)` / `state()` / `subscribe(fn)` | 状态查询与订阅（UI 刷新用） |
| `persist(passphrase, ttlMs?)` | 用口令加密暂存（默认 8 小时） |
| `unlock(passphrase)` | 解密恢复到内存，失败返回 `false` |
| `lock()` / `purge()` | 锁定（留密文）/ 彻底销毁（连密文一起删） |
| `handleFor(slot)` / `isHandle(v)` | 生成 / 判断配置里那个不能发请求的句柄 |
| `secureFetch()` / `authHeaders()` | 唯一允许携带 Key 的请求出口 |
| `mountVaultControls(host, onChange?)` | 挂载本文对应的原生 DOM 控制面板（含「?」说明按钮） |

面板全程用 `createElement` + `textContent` 构建，**不拼接 HTML 字符串**，因此说明文本本身不构成注入面；站点 CSP 也需要允许对应的外部脚本文件。
